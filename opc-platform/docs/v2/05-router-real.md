# Router 要真的像 Super-agent 的 Router

> 靶子：Super-agent 设计探索 §2.1 / §2.2 / §3 / §4.1 / §6
> 前置：`04-superagent-check.md` 是方向核对；这份是**落地口径**。
> 这一版按原文的五件事组织：触发链路、两层过滤、路由转发（Router 负载）、Thread、
> Inline & Spill。每一节都写清"落到哪个文件"和"凭什么说它成立"。

## 0. 整条链路

```
  GitHub ─┐                       ┌──────────────────────────────────────┐
  飞书   ─┼─► POST /hook/<source> │ trigger/  认人 → 验身 → 归一 → 落事件 │
  钉钉   ─┤   （签名校验、去重）    └───────────────┬──────────────────────┘
  文件夹 ─┤                                        │ event(source, kind,
  聊天   ─┘                                        │       payload.threadKey)
                                                   ▼
                              ┌────────────────────────────────────────┐
                              │ Router.tick —— 确定性，不花 token        │
                              │ ① 程序层过滤（triage.ts）                │
                              │ ② 归属查表（threadKey → 订阅者）          │
                              │ ③ 语义门（可配：semanticGate.ts）        │
                              │ ④ 冷启动 / 协调：攒批交给 Router 会话      │
                              └───────┬────────────────────┬───────────┘
                       有订阅者 │                             │ 没有归属
                                ▼                             ▼
                  ┌──────────────────────┐    ┌──────────────────────────────┐
                  │ 直接派给执行体          │    │ Router 会话（常驻 LLM）        │
                  │ 不经过 Router，不花 token│    │ agents/router.sqlite · 7 个工具│
                  └──────────┬───────────┘    └──────────────┬───────────────┘
                             │                               │ open_line_of_work
                             │                               ▼
                             │                ┌──────────────────────────────┐
                             └───────────────►│ 执行体（自己的 sqlite、工具集） │
                                              │ 干活 → 闸门 → report           │
                                              └──────────────┬───────────────┘
                                                             │ report(level)
                                                             ▼
                                             报告回来：silent 留在记录里，
                                             decide/notify 下一轮进 Router 上下文
```

一句话：**事件量增长的一侧是 ② 那条支路，Router 只在 ④。** 这就是负载答案。

## 1. 触发链路（原文 §3 Trigger）

| 要什么 | 在哪 | 凭什么说它成立 |
|---|---|---|
| 多来源接入 | `trigger/{github,feishu,dingtalk}.ts` + `trigger/server.ts` | `trigger/*.test.ts`：用各家真实的 payload 形状驱动 |
| 新来源不改调度循环 | `TriggerRegistry` 一行注册 | `router.ts` 里没有任何来源名 |
| 签名校验 | `trigger/verify.ts` | 没配密钥 = **拒绝**，不是放行；比较用定长时间函数 |
| 重投不重复派活 | `event.dedupe_key`（V35 偏唯一索引） | `ingest.test.ts`：同一投递 id 两次 → 一条事件 |
| 结束信号 | `terminal` → 程序直接收线 | PR 合并后那条线不再等人；手上还有活就不收 |

每一家适配器只做一件事：**把方言归一成"这件事是什么 + 它是哪个外部东西的影子"**。
它不判断值不值得做（那是两层过滤），也不开线（那是 `open_line_of_work`）。

飞书 / 钉钉有一条必须说清的规则：**单聊不并线**。单聊是你跟助手说话的信道，与桌面聊天
窗口是同一件事；给它一个身份，一旦某条线订阅了那个键，你后面说的每句都会被直通给
执行体，Router 再也听不到人说话——聊天链路上已经踩过一次这个坑。群里的话题才开线。

**没做的**：polling（凭 token 主动拉）。三家都只走 webhook；要从公网收到推送，中间需要
一条隧道（`cloudflared` / `ngrok` / 自己的反代），这一步由使用者决定，我们不假装做了。

## 2. 两层过滤（原文 §3.1 Fast / Slow Path）

| 层 | 花多少 | 谁在判 | 可配成 |
|---|---|---|---|
| 程序层 | 零 token | `router/triage.ts` 三条规则：自己写出来的回环、没有正文、窗口内重复（**人的话不去重**） | `noise`（默认）/ `allowlist` |
| 语义门 | 一次分类调用，按批摊薄 | `router/semanticGate.ts` → `decisions.classify`，一批一次、每批最多 10 条 | `router`（不设门）/ `decision`（先过分类器） |
| 主判 | Router 的上下文 | Router 会话：开不开线、派给谁、怎么跟你说 | 不配——它需要连续上下文 |

原文说语义层是"由 LLM 按**用提示词编写的策略**判断是否需要行动"。所以策略本身是配置：
`TriagePolicy.semanticPrompt`，设置 → 调度 → 语义层 里是一段可编辑的提示词。写死在
源码里等于让写代码的人替所有用户决定"什么算噪声"——跑发布的人希望 CI 绿了是噪声，盯
代码的人希望它是一条事件。

三个决定是有意为之：

1. **语义判断被拆成两个问题**。①「值不值得占用上下文」廉价、可批量、不需要全局视野，
   交给分类器；②「要不要开线、派给谁」需要连续性，永远是 Router。
2. **两层的失败方向都是"往上交"**：规则拿不准就放行；分类器没配、调用失败、答案缺失
   也一律放行。省钱的层没有丢活的权力——`TriagePolicy` 调的是花多少钱，不是活会不会丢。
3. **配置存 `app_setting`（`router.triage`），每轮重新读**。改完下一轮生效，不需要重启。

## 3. 路由转发与 Router 的负载（原文 §3.2 + §3.3）

### 3.1 直通

事件带 `payload.threadKey` → `threadByKey`（部分唯一索引，一个身份只有一条活线）→
`subscribersOf` 非空 → 直接 `openLine`，**不经过模型**。

- **直通带上人**：`openLine` 收 `workerId`，归属已定就不再按目标挑一次人。
- **事件带上正文**：直通省掉的是"判断"，不是"信息"。
- **顺序有保证**：同一执行体的派活进 `work/ownerQueue.ts` 的 FIFO 队，一个接一个跑。
  没有这条队，同一份 PR 的 5 条评论会并发写同一个 sqlite 会话并把 harness 毒化。

### 3.2 Router 只剩两件事

到 ④ 的只有两种东西：**没有归属的新事件流**和**要开口说的汇报**。

这里曾经有个窟窿：一次正常交付的汇报是 `silent`（"干完了，只在记录里"），它也被塞进
Router 的输入，于是**每完成一件正常的事就要花一轮推理**去得出"不用说"这个永远相同的
答案。功能一点没坏，测试也不会红，只有账单知道。现在 `silent` 不进那个队列。

可测的口径（`router.test.ts`「Router 的负载」）：

| 场景 | 直通 | Router |
|---|---|---|
| 同一身份上 20 条事件 | 20 | **0** |
| 20 条没有归属的事件 | 0 | 1（一条输入，不是 20 次） |
| 一次成功交付（silent） | — | **0**，记录还在 |
| 一条 decide 汇报 + 一条事件 | — | 1（同一份输入） |

**直通关掉会怎样？** 功能不丢，只是贵一些（原文实测读缓存 token 约 +30%）。
**语义门关掉会怎样？** 也一样。两条都写在用例里——它们证明这两层是优化而非正确性。

## 4. Thread（原文：具备连续 / 完整上下文的 request）

一个 GitHub PR、一封邮件的往来、一个 IM 话题能被称为"一条线"，靠的是**外面那个东西
自己有一个 id**，不是我们给它起了个标题。所以身份的形状是 `<source>:<externalId>`：

```
github:acme/api#128          一个 PR（它下面的评论、CI 结论都落在这里）
github:acme/api@main         一条分支的推送流
im:feishu:oc_xxx:om_yyy      飞书某个话题
im:dingtalk:cidAAA           钉钉某个群会话
```

| 设计问题 | 怎么做 | 为什么 |
|---|---|---|
| 身份怎么归一 | `router/threadKey.ts` 的 `threadIdentity()`：去空白、带上来源前缀、长度上限 | 并线键是**身份**不是文本：`PR #12` 与 `PR  #12` 算两条线的话，这种分裂永远不会有人发现 |
| 一个身份能有几条线 | 一条（V35 部分唯一索引，终态线不占位） | 老代码只按 `last_activity_at` 取最新，重复键不报错、只让旧的那条变成永远收不到事件的孤儿 |
| 开线是幂等的吗 | `ThreadRepository.openThread()`：有就并进去，没有才建 | 直通与 Router 会**同时**走到这里，`查一次再建`之间的窗口会让同一个 PR 前两条评论建出两条线 |
| 什么时候结束 | 外部结束信号（PR 合并、issue 关闭）→ 程序直接收线 | 结束是外部事实，不需要问模型；手上还有活就不收 |
| 顺序 | 同一执行体的队列串行 | 一条线一个主执行体（`subscription` 多对多的意思是"一个执行体盯多条线"，不是"一条线找一堆人抢"） |
| 上下文在哪 | 线自己的 `goal` + 任务 + 汇报，`recall <threadId>` 一次取回 | 线不需要把 200 条事件装进窗口；它需要的是"现在到哪一步了" |

## 5. Inline & Spill（原文 §3.3）

一句话：**把能读懂的那部分放进上下文，把剩下的留在库里，并告诉模型去哪读。**

"截断"给模型的是一句被砍断的话和一个它不知道自己漏了多少的黑洞。Spill 给的是**可推断
的摘要**：开头、结尾、一共多大、去哪读全的。

| 约束 | 实现 |
|---|---|
| 预算属于**一次输入** | `perItemBudget()`：总 6000 字，单条 floor 160 / ceiling 1200，按条数分摊 |
| 切在行边界上 | 头 65% 行 + **从末尾往回数**的尾 25% 行；中文没有空格，按字符切会切开词 |
| 结论在最后 | 尾部从末尾倒数（CI 的失败原因、日志的报错、邮件的落款都在这儿） |
| 标出漏了多少 | `…（略去 N 行）…` + 末尾"共 N 行 / M 字" |
| 单行超长 | 退回按字符切，但保住尾部 |
| **读侧也限长** | `recall` 分页（`recall <id> 2`）：把全文倒回上下文等于把 spill 白做了 |
| 两层看到同一段 | 语义门用同一个 `spillText`（300 字） |
| 无损 | 全文永远在库里；spill 只决定这次显示多少，从不删除、从不总结 |

有一条用例是**性能断言**而不是格式断言：40 条长事件合起来不超过预算 + 固定开销。
没有它，成本会随"这一轮恰好来了多少条 × 每条多少字"浮动。

## 6. 逐条对齐

### §2.1 Router 层

| 原文要求 | 实现 | 位置 |
|---|---|---|
| 常驻，承接所有入口的人类交互 | 一个 durable conversation，`Harness.root()` | `routerSession.ts` |
| 全局序点、协调点、记忆 | 会话历史 + `list_lines` + `recall` + `remember` / `recall_memory` | 同上 |
| **不直接执行具体任务** | 注册表里没有 bash / 读写文件 / 代码执行 | `routerTools.ts`（有测试锁住） |
| 可以配轻量模型 | 工作台默认模型，`thinking` 默认 low | `routerHost.ts` |
| 批处理 | 交给 pi 的 inbox：忙时排队，下一个 boundary 合成一次调用 | `routerSession.deliver` |
| 「记忆」不只是上下文窗口 | `remember` / `recall_memory` 读写 `owner_id = 'router'` | `routerHost.ts` |
| 「规矩」不只执行体知道 | `fact` 的 global 几条每轮拼进输入 | `router.composeInput(rules)` |

### §2.2 Worker 层

| 原文要求 | 实现 |
|---|---|
| 上下文隔离 | 每个 worker 一个 harness（`agents/<workerId>.sqlite`） |
| 挂载完整执行工具 | `toolSlots` / `buildRegistry`（workService） |
| **不直接与人类交互** | 执行体没有聊天出口，只能 `reportToThread` |
| 向 Router 汇报、由 Router 统一回复 | `report` 表 → 下一轮进 Router 上下文 → `reply_to_user` |
| 一线多 worker / 一个 worker 多条线 | `subscription(thread_id, worker_id)` |
| **同一时刻只跑一个任务** | `work/ownerQueue.ts`（正确性：并发写同一 sqlite 会毒化会话） |

### §4.1 全双工

派活本身就是异步的：`open_line_of_work` 建任务、`startTask`、**立刻返回 id**。
Router 这一轮推理到此结束，结果之后作为汇报回来。

### §6 Watchdog

程序层（spinning / stalled / orphaned）已有。**模型层还没有**——判断"方向是否偏离"需要
读执行体的过程，等事件量上来再说。

## 7. 扩展性：加东西不用改调度循环

| 要加什么 | 加在哪 | 不改什么 |
|---|---|---|
| 新的触发来源（日历、邮件、Linear） | `trigger/` 一个适配器 + 注册一行 | `router.ts` 一行不动 |
| 新的 Router 动作（如"合并两条线"） | `routerTools.ts` 里加一个 `defineTool` | 调度循环、会话层 |
| 新的执行体类型 | `WorkerTemplate` + `toolSlots` | Router |
| 换模型 | 设置里换默认模型，下一轮生效 | 无 |
| 换过滤策略 / 判噪策略 | 设置 → 调度 | 重启、代码 |

## 8. 还差什么（诚实清单）

1. **触发源的 polling**：没有。只有 webhook；公网可达要靠隧道。
2. **投机执行（§3.4）**：没有。它需要"后台有富余算力"的前提，单机串行跑 worker 时
   提前做只是抢同一个人的时间。
3. **Watchdog 的模型层（§6）**：没有。程序层在，语义层没接。
4. **计算/状态/环境分离（§5）**：不做。本地优先桌面应用三者天然合一；代价是「持久」
   只到进程级（`resumeInterrupted`），关机就停。
5. **多 Router 分片（§2.1 后半）**：不做。单机事件量远没到瓶颈，过早分片会拿全局连续性
   换吞吐；而且 ② 那条直通支路已经把绝大部分负载挡在 Router 之外了。
6. **被程序层丢掉的事件没有界面入口**：`event.triage = 'dropped'` 留在库里，
   `recall <eventId>` 也能取到，但没有任何页面列它们。这是**可见性缺口**，不是正确性缺口。
7. **线级摘要**：`recall <threadId>` 给的是结构（任务 + 最近汇报），不是一段写好的叙述。
   写叙述要一次模型调用，现在判断为不值——先把结构看全，需要叙述时再说。
8. **记忆还只是一张扁平表**：关于「这个人」的记忆被切在每个执行体名下，衰减被当成删除用，
   没有常驻层，写入靠提示词自律且无去重。四条都有代码位置和真实库上的数字，
   设计口径见 `07-memory.md`。

## 9. 你中途改方向真的通了（§8.2）

| 时刻 | 机制 | 你看到 |
|---|---|---|
| **正在跑** | 插进那个会话：`conversation.submit({ whenBusy: 'steer' })` | 「已经插到正在跑的活上」 |
| **还没开跑 / 要重试** | 写进 `task.steering`（V32），`produce` 每次重新读 | 「记在这条线上了，开跑时会看到」 |
| 已经收尾 | 拒绝，理由说清楚：改方向得开新线 | 「这条线上的活已经收尾了」 |

提示词里的顺序是有意义的：改方向排在原始说明**之后**，并且明确写着"与上面的说明冲突
时，以这里为准"。否则话存进库了、执行体照旧按原说明干，你会以为自己的话没被听见。
