# 记忆：个人助手的最后一公里

> 靶子：Super-agent 设计探索 §2.1（Router 是「序点、协调点和记忆」）+ CoALA 的五类记忆。
> 前置：`05-router-real.md` §2.1 的「记忆」一行、`06-vocabulary.md` 的 V33。
> 这份是**设计口径**。第 10 节有分期；**P0 已落地**（见 §14），P1 之后还没动。

## 0. 三条结论

1. **现在最大的问题不是检索不够聪明**，是两件基础设施级别的事：关于「这个人」的记忆被切成了
   N 份（每个执行体一份，Router 一份），以及**衰减被当成删除**用（低于阈值就查不出来）。
2. **最重要的偏好不该走「按需检索」**。模型不会主动去问。必须有一个常驻层。
3. **写入质量决定系统质量**，检索是次要问题。而写入侧现在最大的浪费是：**用户返工的理由**
   这个信号完全没被用上。

---

## 1. 第一性原理

### 四条公理

**A1. 记忆的单位不是「事实」，是「被替代掉的决策」。**

存一条「他喜欢先给结论」，价值不在那句话，在以后**不用再问一遍**。所以衡量一条记忆的唯一
标准是：它替用户省下了多少次重复解释。存了但永远不用的记忆，成本是负的（占检索名额）。

**A2. 代价不对称，而且有三层，不是两层。**

| 失败 | 代价 | 例子 |
|---|---|---|
| 违反一条已经说过的约束 | 最高 | 他明明说过「别写注释」，又写了 |
| 应用了一条错误的推断 | 高 | 一句随口的话被当成长期偏好，之后一直被这么对待 |
| 忘掉一条用不上的记忆 | 低 | 确实不重要 |
| **忘掉一条重要的记忆** | **流失** | 他必须重新解释一遍自己是谁 |

「一次记忆的衰退都会损失掉一个用户」，在 A2 里是最后一行——**不常发生，但每次不可恢复**。
所以遗忘的代价不是线性累积，是阶跃的：平时感觉不到，感觉到的那一次就转身了。

**A3. 记忆有不同的时间常数。**

「他最近在做一个 Rust 项目」会过期；「他讨厌客套话」不会。一条衰减曲线套在所有记忆上，
必然要么让稳定的记忆过早衰退，要么让易变的记忆变成陈旧谎言。

**A4. 必须每轮生效的东西，不能依赖模型主动去取。**

「模型记得去问」不是可靠性，是概率。称呼、语气、格式禁令这类东西一旦漏一次，用户看到的是
「它又忘了」。

### 由此推出的四条硬规则

| 规则 | 来自 |
|---|---|
| **衰减只影响排序，永不影响可达性。** 任何「低于阈值就不返回」都是删除设备，必须从显式查询路径上去掉 | A2 |
| **关于一个人的记忆只存一份，全系统共用。** 存在「这个人」名下，不是存在某个执行体名下 | A1 + A2 |
| **最重要的那一小撮偏好每轮都在上下文里**，不靠检索 | A4 |
| **记忆必须能被看见、被改、被删。** 看不见的记忆等于赌博 | A2 |

## 2. 现状

### 2.1 四条链路各自在干什么

| 链路 | 代码 | 写什么 | owner |
|---|---|---|---|
| A. Router 主动记 | `routerHost.remember` ← `remember` 工具 | `kind='preference'`，`scope=personal` | `ROUTER_ID`（`'router'`） |
| B. 会话归档巩固 | `chatService.sweepIdleConversations` → `memory/consolidation.ts` | 模型总结出的 lessons | `conversation.memberIds[0]` |
| C. 任务通过验收 | `workService` 的 `onFinished` | `kind='experience'`，`scope=thread` 或 `personal` | `task.assigneeId`（**执行体**） |
| D. 规矩（不是记忆） | `fact` 表，`routerHost.rules()` 每轮取 12 条 | 人手工写的长期约定 | 无 owner，`scope_type='global'` |
| 读 | `recall_memory` 工具 / `recallMemories`（执行体） | — | 见下 |

读取有两个入口，取的东西不一样：

```ts
// Router：owner = 'router'，作用域 = personal + 最近 5 条活跃线
deps.memory.retrieve({ ownerId: ROUTER_ID, query, scopes: [{type:'personal'}, ...lines], limit: 5 })
  → items: string[]        // ← 只留正文，id / kind / scope / score 全丢

// 执行体：owner = 自己，作用域 = 那条线 + personal
deps.memory.retrieve({ ownerId: task.assigneeId, query, scopes: [thread, personal], limit: 5 })
```

### 2.2 四个结构性问题

**问题一：同一个人被切成了 N 份记忆。**

`personal` 的实参是 `task.assigneeId`——**那个执行体自己的**。于是用户说过的一句
「以后结论放前面」：Router 记在 `router` 名下，执行体 A 读自己的，执行体 B 读自己的。
关于同一个人的偏好被切成 N+1 份，谁也不知道谁记了什么。

这不是实现细节，是**命名把概念搞错了**：`personal` 的本意应是「关于这个人的」，而不是
「关于这个 agent 实例的」。

**问题二：衰减被当成了删除。**

```ts
// memoryScore.ts
filter(entry => entry.strength >= minStrength /* 0.2 */ && entry.score > 0.02)
```

半衰期 30 天、floor 0.05。一条记忆 90 天没被召回，强度掉到 0.125，**低于 0.2，永远查不出来**。
而 `recall_memory` 是唯一入口，没有「列出全部」。

结论：这是一个**静默删除机制**，删的时候不告诉任何人。第 91 天恰好需要它的那次，就是流失。

**问题三：没有常驻层。**

最该「永远生效」的东西（称呼、语气、格式禁令）全躺在只能按需检索的表里。Router 在回答
「帮我看下这个」时不会去调 `recall_memory`。

执行体那边有个类似常驻的东西（`fact` 的 `global`，每轮 12 条拼进输入），但那是**人手工写的
规矩**，不是从使用里习得并升级上来的。

**问题四：写入靠自律、无类型、无去重。**

- 触发条件是 `routerTools.ts` 角色提示词里的一句祈使句（「听到『以后都这样』『别再做 X』
  这类要求，用 remember 记下来」）
- `kind` 恒为 `'preference'`
- 无条件 `INSERT`：同一件事说三遍就是三条，之后三条挤占 5 个名额里的 3 个
- `remember` 返回的 id 在工具层被丢掉（`ok('记住了。')`），用户看不到「记了什么」

### 2.3 在真实库上的核对

这台机器上的 `company.db`（v1 时期用过的库，`thread` / `report` 都是 0 行）：

| 事实 | 数字 | 说明 |
|---|---|---|
| 记忆总数 | 289 | 全部 `is_archived = 0` |
| owner | **全部挂在一个 `agent-8669…` 上** | 当前 worker 是 `d6b8828d…`，`router` 名下 **0 条** |
| `kind` 分布 | `experience` 185 / `fact` 84 / `preference` 20 | 情景记忆占 64% |
| `scope` 分布 | `personal` 289 / `thread` 0 | 代码支持 thread 作用域，一条都没用上 |
| `source_type` 分布 | `consolidation` 255 / `task` 34 / **`manual` 0** | **`remember` 工具从来没被真正用过** |
| 有 embedding 的 | **0** | 权重里那 0.55 的语义相似度，在实际数据上从未生效 |
| strength | 全部在 1.0–1.5 | 衰减还没开始咬人（数据还新） |

这张表把四个问题全部量化了：

- 289 条记忆的 owner 既不是现在的 worker，也不是 `router`——**所有关于这个人的历史，目前没有
  任何代码路径读得到**。
- `manual = 0`：靠提示词自律的写入口，在真实使用里是**死的**。
- `embedding = 0`：向量检索的收益是纸面上的。
- `experience` 占 64%：这些是「任务通过验收」的过程记录，属于情景记忆，却和「他讨厌客套话」
  挤在同一个 `personal` 作用域里，稀释偏好检索。

> 关于 owner 孤儿：这是 V33 的既定取舍——「宁可旧数据显示不全，也不在迁移里猜一个 worker 出来」。
> 那条决定本身没错。缺的是**给这些行一个能被认领的出口**：它们该挂在「这个人」名下，
> 而不是挂在某个已不存在的 agent 上。修法不是再猜一次，是引入用户命名空间 + 一个认领界面。

## 3. 分类学：先分清存的是什么

用 CoALA（*Cognitive Architectures for Language Agents*, Sumers et al. 2023）的五分，落到我们产品上：

| 类型 | 内容 | 时间常数 | 现存位置 |
|---|---|---|---|
| **Working** | 这一轮推理的上下文 | 分钟 | Router 会话 + 线上下文 ✅ |
| **Episodic** | 一段经历：这条线干了什么、为什么返工 | 周到月 | `report` 表 + `experience` 记忆 ⚠️ 混在 personal |
| **Semantic** | 关于用户/世界的稳定事实 | 月～永久 | `memory`（无类型）⚠️ |
| **Procedural** | 怎么做事：格式、验收标准、工具偏好 | 月 | worker 的 `tool_policy` + prompt section ✅ **但从不更新** |
| **Prospective** | 将来的事：提醒、承诺 | 到点为止 | ❌ 没有 |

两条直接推论：

1. **五类必须分开存**。它们的读写时机、衰减方式、失效方式全不一样。现在四类挤在一张表里，
   用一个 `kind` 字符串区分，只有一条衰减曲线——这是结构性问题，不是参数问题。
2. **程序性记忆我们已经有地方放了**（执行体的 prompt section 与 `tool_policy`），但它**从来
   不会被更新**。用户三次要求「先给结论」，第四次执行体还是按默认格式干。这是设计上最大的
   浪费：地址有了，信没投。

## 4. 目标结构

### 4.1 三层

| 层 | 名字 | 容量 | 读取时机 | 衰减 | 谁能写 |
|---|---|---|---|---|---|
| **L0** | 铁律（standing constraints） | ≤ 20 条，硬上限 | **每轮进上下文** | **不衰减** | 用户明说；或重复观察到 N 次后晋级 |
| **L1** | 长期记忆（typed） | 数千条 | ① 拼输入时自动注入 top-3 ② 显式 recall | 只影响排序 | 抽取管线 / 用户 |
| **L2** | 情景档案（episodic） | 不限 | 按 id 或时间窗取，不参与主动检索 | 只归档 | 任务结束 / 会话归档 |

### 4.2 L0 是这一版的关键

L0 存的是「违反了就会被指出来」的东西。它解决 A4：**不依赖模型想起来**。

- 容量硬上限 20 条。超了必须合并或淘汰——这个约束本身是好事，它逼着系统只升级真正重要的。
- 每条必须是**可执行的约束**，不是描述。所以写入时要过一道改写：
  「他好像比较喜欢简洁」→「回答控制在三句以内，不复述他的原话」。
- **永不自动消失**。只能被用户撤销，或被一条更新的同主题约束取代（旧的留档）。

### 4.3 字段

`memory` 表已经有的：`owner_id` `kind` `content` `scope_type` `scope_id` `source_type`
`source_id` `valid_from` `valid_until` `strength` `recall_count` `last_recalled_at`
`is_archived` `embedding`。

缺的四个字段，每个都有明确用途：

| 字段 | 为什么必须有 |
|---|---|
| `subject` | 规范化主题键（`output.format`、`person.客户A`）。**这是去重与冲突消解的支点**；没有它，「同一件事说三遍」永远合并不了 |
| `volatility` | `stable` / `slow` / `session`。A3 落地：衰减曲线按它选，不再全局一条 |
| `confidence` | 由**证据类型**决定，不由模型自评：用户明说 1.0 / 返工三次 0.7 / 巩固摘要 0.5 |
| `superseded_by` | 被新版本取代时指向新条目，**不删旧行**。这是「永不删除」的配套条件 |

`valid_from` / `valid_until` 已经在表里但**没人用**。它们对应 Zep / Graphiti 的双时间思想：
让「他以前喜欢 A、现在喜欢 B」同时存在，而不是互相覆盖。

这里有一个值得记下的对照：**`fact` 表已经有 `subject` / `predicate` / `object` / `confidence` /
`valid_from` / `valid_until`，`memory` 表一个都没有。**

```
fact    : company_id, scope_type, scope_id, subject, predicate, object, statement,
          source_type, source_id, valid_from, valid_until, confidence, is_archived, ...
memory  : owner_id, kind, content, scope_type, scope_id, source_type, source_id,
          valid_from, valid_until, strength, recall_count, last_recalled_at, is_archived, ...
```

更成熟的 schema 长在**没人学习的那张表上**（`fact` 是人手工写的，84 行全是 global）；
会从使用里长出来的那张表反而是扁平的。这不是疏忽，是两条链路各自演化、没有统一口径的结果。
P2 要做的事，本质是把 `fact` 已经想清楚的三个字段（`subject` / `confidence` / 双时间）
补到 `memory` 上，而不是另发明一套。

### 4.4 命名空间

| 归属 | `owner_id` | 读 | 写 |
|---|---|---|---|
| 关于**这个人** | `USER_ID`（`'user'`） | Router、所有执行体、界面 | Router（**执行体不可写**） |
| 关于**这条线** | `thread.id` | 这条线上的执行体、Router | 执行体、Router |
| 关于**这个执行体怎么干活** | `worker.id` | 它自己 | 它自己 |

铁律：**执行体不能写关于人的记忆**。一个执行体的错误推论不该污染全局认知。

这一条同时解决 2.2 的问题一。

> P0 只换了归属键，**没有新加 `worker` 这个 scope 值**（那要改 CHECK 约束，属于 P2）。
> 所以现在 `personal` 有两个归属可能：`owner='user'` 是「关于这个人」，
> `owner=<worker id>` 是「这个执行体自己的习惯」。靠 owner 区分，不靠 scope 猜。

## 5. 写入管线

按 LangMem 的术语，把写入从 **hot path** 移到 **background path**，但保留一条「用户明说」的快车道。

```
      ┌─ 快车道（同步）：用户说「记住…」→ 立刻写 L0/L1 → 回执 → 可撤销
      │
信号 ─┤
      └─ 慢车道（异步，一批一次）
           ① 收候选 → ② 抽取 → ③ 冲突消解 → ④ 晋级 → ⑤ 落库
```

### ① 收候选：先榨干免费信号

现在的输入只有「用户对 Router 说的话」。系统里已经有三个**极强且免费**的偏好信号，一个都没用：

| 信号 | 在哪 | 为什么是最强证据 |
|---|---|---|
| **返工理由** | `decideThread(threadId, 'rework', note)` 的 `note` | 用户明确说「这版不对，改成 X」——比聊天里随口一句可靠得多 |
| **中途改方向** | `steer_line` 的 note（`task.steering`） | 同上，而且是「原来的方向错了」的直接证据 |
| **反复纠同一处** | 同一 `subject` 上多次返工 | 一次是偶然，三次是偏好 |

**这是收益最大的一处改动**：不引入任何新调用，只把已有文本接进管线。用户每返工一次，系统就
多问一遍「这是不是一条该记住的偏好」。

### ② 抽取：一次调用，结构化输出

复用现有基础设施（`DecisionService.classify` 那套 `state + questions → 带概率的类型化答案`），
或更合适的一次带 JSON schema 的 extract。输入：这批信号 + **库里相关的已有条目**。

```
{ kind, subject, content, volatility, evidence_span, confidence }
```

必须给模型看已有的相关条目——否则它不知道「这条是不是已经在库里」，只能重复写。

### ③ 冲突消解：确定性优先，模型兜底

Mem0 的 ADD / UPDATE / DELETE / NOOP 方向是对的，但改成三级：

| 级别 | 判断 | 成本 |
|---|---|---|
| 一级 | `subject` 精确匹配 + 内容相同 → NOOP | 0 |
| 二级 | `subject` 精确匹配 + 内容不同 → SUPERSEDE（旧行写 `valid_until`，新行写 `superseded_by`） | 0 |
| 三级 | subject 不匹配但语义近 → 问一次模型（同一条？不同条？） | 一次小调用 |

先把确定性的一二级做完。真实数据里 80% 的情况应该能在这两级解决，那时候根本不需要第三步。

### ④ 晋级：L0 从哪来

- 用户明说「以后都这样」「记住」→ 直接晋级 L0，并要求改写成可执行约束
- 同一 `subject` 被独立观察到 ≥ 3 次 → 晋级（这里用阈值，因为 A2 说「应用错误推断」代价高）
- 晋级时**必须通知用户**：「我记下了一条规矩：…… 不对的话告诉我。」不可见的自动升级是赌博

### ⑤ 落库 + 回执

写入必须带 evidence 指针——**每条记忆都知道自己的原文在哪**。这是 Inline & Spill 在写入侧的
对应物：事件链路已经这么做了（`recall <id>`），记忆链路一条都没做。

## 6. 读取

### 6.1 Push 与 Pull 分开

| 通道 | 内容 | 预算 |
|---|---|---|
| **Push（每轮）** | L0 全部（≤ 20 条）+ 未结的开放事项 | 固定，约 300 token |
| **Pull-auto（拼输入时）** | 用当前事件/汇报的文本做**零成本**的字面匹配，取 top-3，**带 id** | 3 条 |
| **Pull-explicit（工具）** | id + 类型 + 时间 + 出处 + 摘要；可展开取全文；有「列出全部」模式 | 分页 |

Pull-auto 明确是「零成本的字面匹配」：它在拼输入的路径上，每次多一次网络往返是**拿延迟换
不确定的收益**。

### 6.2 显式查询必须绕过衰减

- `recall_memory(query)` → 排序用衰减（合理：相关度要有时效性）
- `recall_memory(query, all)` / `list_memories(kind)` → **完全不看强度**，只按时间排

「永不删除」必须有出口，否则它只是句口号。

### 6.3 返回值必须可寻址

现在 `recallMemory` 返回 `items: string[]`，把 `id / kind / scopeType / score` 全丢了。应该返回
一行摘要 + id，正文按 id 另取。形状要和事件链路对齐：

```
mem-3f2a · 偏好 · 输出格式 · 2026-07-14 · 来自「重做第 2 轮」· 他要求结论放在最前面
```

## 7. 执行侧：让程序性记忆有学习回路

现在的循环断在这里：

```
用户三次返工「结论放前面」 → 每次都要 Router 重新解释 → 执行体第四次还是按默认格式干
```

应该做的：`kind = format | workflow` 的记忆按作用域注入执行体的上下文。

- 个人级（`owner = 'user'`）→ 注入所有执行体
- 线级（`owner = thread.id`）→ 只注入这条线的执行体
- **执行体只读**

这和 Voyager 的 skill library 是同一个思想（把成功的做法固化），但粒度更小、更贴产品：
**不是固化技能，是固化偏好**。

它顺带解决一个具体问题：Router 可能忘，但执行体不会——它的 prompt 是每次现拼的。

## 8. 可见性：这是留存问题，不是 UI 问题

A2 的反面就是：**用户看不见助手记得什么，就不会信任它**。

最小的「助手记得的事」页面必须能回答三个问题：

1. **它记住了我什么？** 按类型分组，每条显示内容、来源、最近一次被用到的时刻。
2. **记错了怎么改？** 编辑、删除、「这不是我的意思」。
3. **它是从哪知道的？** 点开出处 → 那次对话 / 那条线的返工理由。

第三条尤其重要：**能追到来源的记忆才是可信的记忆**。这正是 evidence 指针的产品价值，
也是 `source_type` / `source_id` 这两列存在的意义——它们一直在库里，只是没给任何人看。

顺带：2.3 里那 289 条孤儿记忆的归宿也在这里——做一个「这些是以前记的，还要吗」的认领视图，
比在迁移里猜 owner 诚实得多。

## 9. 度量

| 指标 | 定义 | 目标 |
|---|---|---|
| **重复纠正率**（北极星） | 同一件事被用户纠正两次的比例 | 趋零 |
| 约束违反率 | 输出违反 L0 条目的比例（LLM judge 回归集） | 趋零 |
| 重复提问率 | 助手问了已经被告知过的事 | 趋零 |
| 记忆冗余率 | 同一 `subject` 上的重复条目占比 | < 10% |

前两个是流失的直接前兆，后两个是库的健康度。四个都能离线跑，不靠感觉。

## 10. 分期

按性价比排，不按技术难度：

| 期 | 做什么 | 为什么先做 |
|---|---|---|
| **P0** ✅ | ① 个人记忆收归 `owner = USER_ID`，执行体只读 ② 显式查询绕过衰减 ③ recall 返回带 id/类型/来源 | 三个都是修 bug 级别，改动小，直接止血 |
| **P1** | L0 层（常驻 + 每轮注入 + 上限 20 + 不衰减） | 解决 A4，收益最直接 |
| **P2** | 类型化（`kind` / `subject` / `volatility`）+ 确定性去重与取代 | 让后面所有东西有地方挂 |
| **P3** | 免费信号接入（返工理由、steer note）+ 后置抽取管线 | 收益最大，但依赖 P2 |
| **P4** | 晋级到 L0 + 记忆界面（看 / 改 / 删 / 追来源） | 信任 |
| **P5** | 程序性记忆注入执行体 | 学习回路闭合 |
| **P6** | 向量检索（只对 L1 子集） | 收益最不确定，最后做 |

**不建议一开始做 embedding。** P0–P5 全是确定性工程，每一项都有明确验收方式；向量属于概率
收益。真实库上 `embedding` 列 0 行，就是最好的说明。

## 12. 不做的，以及自我反驳

**不做的：**

- **图数据库 / 知识图谱**。单机、单人、几千条记忆，`subject` 精确键够用。上图的复杂度换不来
  产品收益。
- **自动 reflection 循环**。已经有「会话归档 → 巩固」，再加一层只是加钱。
- **embedding 全表扫**。要向量也是先按时间窗 + 作用域缩子集，再算。
- **让执行体写个人记忆**。一个执行体的错误推论不该污染全局认知。

**对自己这套设计的反驳：**

1. **可能过度设计。** 单机助手的真实记忆量是几百条量级。如果 P0 + P1 能解决 80% 的问题，
   P3 的抽取管线就只是精致。**所以它排在 P3，不排在 P1。**
2. **后置写入有延迟。** 用户说「记住 X」必须立刻生效，不能等后台。所以快车道是必须的，
   慢车道只处理推断出来的东西。
3. **L0 上限 20 条会溢出。** 重度用户可能有 40 条硬约束。届时的解法不是提高上限，是
   **按场景聚类**（「写代码时」/「写文档时」），只注入相关那一组。第一版不做。
4. **「永不删除」会积累矛盾。** 所以 `superseded_by` + 双时间不是可选项，是配套条件——
   没有它，「不删」会变成「自相矛盾」。

## 14. P0 已落地（这一节是完成报告）

三件事，都带着能复现原 bug 的用例。

### ① 归属收归「这个人」

新增 `memory/owners.ts`：`USER_MEMORY_OWNER`（`'user'`）+ `recallOwners()`。三个域并列：

```
'user'        关于这个人    ← Router 写，所有人读
thread.id     关于这条线    ← 谁干谁写，换人还在
worker.id     这个执行体自己的习惯
```

改到的写入口：

| 位置 | 之前 | 现在 |
|---|---|---|
| `routerHost.remember` | `ownerId: ROUTER_ID` | `USER_MEMORY_OWNER` |
| `chatService` 巩固 | `memberIds[0]`（助手会话是 `'router'`） | 助手会话映射到 `USER_MEMORY_OWNER` |
| `workService` 验收通过 | `task.assigneeId` | `task.threadId ?? task.assigneeId` |
| `workService` 的 `remember` 工具 | `personId` | `threadId ?? personId` |

读取侧 `retrieve` 从 `ownerId: string` 改成 `owners: readonly string[]`——一个 owner 的接口
做不到「既读人的偏好，又读这条线的经验」，而这两样必须同时在场。

执行体现在读 `[user, 它的线程, 它自己]`，所以 Router 记下的偏好第一次能到干活的人手里。

### ② 衰减只改排序

`rankMemories` 的 `minStrength` 默认从 `0.2` 改成 `0`，并把「相关度」从「排序分」里拆出来：

```
relevance = semantic*0.55 + lexical*0.30      ← 门槛看这个
score     = relevance + strength*0.15 + 加成   ← 排序看这个
```

拆开是因为一个**一直没被发现的 bug**：总分里带 `strength*0.15`，于是一条新鲜但毫不相干的
记忆也能拿 0.15 分，而门槛是 0.02——**噪声过滤从来没有生效过**，自动召回每次都硬凑满 5 条。

显式回忆（`recall_memory`）传 `minRelevance: 0`：一条都对不上时给出「我记得最牢的几条」
并在输出里说明，而不是回一句"没有记录"。

### ③ 可寻址

`MemorySnippet` 补上 `scopeId / createdAt / sourceType / sourceId / relevance / strength`
（`strength` 是**衰减后**的值）。`recall_memory` 的输出变成：

```
- mem-3f2a · preference · 2026-07-14 · consolidation · 文档放 README 里就够了，别单开 wiki
```

`recall <id>` 现在也能取记忆（和 thread / worker / task / event / report 一样），
`remember` 把 id 放进工具结果的 `details` 里。

### 还没解决的

- **旧库里的孤儿行还是孤儿**。真实库上 289 条记忆挂在 `agent-8669…`，P0 只保证**新写的**
  落在正确归属上。那些行的出口是 §8 的认领界面（P4），不是迁移里猜一个 owner。
- 类型、去重、常驻层、程序性记忆注入，都还按 §10 的排期在后面。
