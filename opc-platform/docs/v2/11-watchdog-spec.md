# Watchdog：主系统之外的另一个执行体

> 靶子：`04-superagent-check.md` §6 与原文 §6（持久在线靠外部 Watchdog）。
> 起点：`watchdog/watchdog.ts` 是一个每分钟跑一次的**纯函数**（已删除）。
> 这份文档定义那一层要变成什么，并记录每一版落到了哪。

---

## 0. 一句话

**Watchdog = 独立进程里的独立 Agent Session**，由定时消息驱动，读同一个业务库，
用程序层筛候选、用模型判方向，发现问题就落 `incident`；
能修的只有白名单里的可逆动作，永远不杀任务。

两条轴必须分开，它们解决的不是同一个问题：

| 轴 | 解决什么 | 兑现方式 |
|---|---|---|
| **独立会话** | 能理解、能追问、能被你问、能管自己的上下文与额度 | 一个独立的 Agent Session（自己的模型档位、自己的会话库） |
| **独立进程** | 主进程卡死 / 崩了，它还活着 | 由主进程启动的 Watchdog 子进程，**不是**主进程里的一个 `setInterval` |

只做会话 → 主进程卡死时它一起死，"外部"没有成立。
只做进程 → 里面还是一个规则表，判不了方向、也问不了话。

**范围**：第一版的生命周期跟着应用走（应用退出它就退出）。"应用关了它还在盯"
是系统服务/daemon 的活，单独立项，不混进这一版。

---

## 1. 它在系统里的位置

```
Electron 主进程
  ├─ 业务服务：任务 / Router / Worker / MCP
  ├─ 写心跳与系统故障事件（system_heartbeat / system_event）
  ├─ 执行 Watchdog 通过 IPC 请求的白名单动作
  └─ 启动、监测、关闭 Watchdog 子进程
           │  （只读业务库 + 自己的会话库）
           ▼
Watchdog 子进程
  ├─ 独立 Agent Session + 独立模型配置（default.watchdog）
  ├─ 定时循环：程序先筛候选 → 有候选才叫模型
  ├─ 只读工具：任务、trace、系统事件、incident
  └─ 写 incident；要动手时发 IPC 请求（不直接改任务状态）
```

### 为什么修复不直接写库

主进程卡住时，Watchdog 即使活着，也不该直接改 `task` 表来"修好它"——
那会把一个正在收敛的运行判死，也会绕过 TaskRepository 的所有不变量。
所以：**发现、诊断、记录可以自治；业务动作必须回到主进程执行。**

## 2. 数据

### 2.1 业务库（现有 company.sqlite，WAL）

| 表 | 用途 |
|---|---|
| `system_heartbeat` | 主进程还活着吗；`instance_id` 用来区分"上一轮进程"与"这一轮" |
| `system_event` | 结构性故障（Router 会话失败、resume 失败、MCP 连不上…）。以前这些只进 `console` |
| `incident` | Watchdog 的判断与生命周期（见 §2.3） |

`system_event` 只存**可安全展示**的字段：类型、时间、关联对象、一句摘要、
一段脱敏过的 JSON。**不存凭据、不存完整提示词。**

### 2.2 会话库（独立文件）

Watchdog 自己的 durable session、上下文滚动摘要、用量。
不放进业务库：模型对话历史与业务数据是两种生命周期，混在一起会让备份、
迁移、清理都变复杂。

### 2.3 `incident` 状态机

```
active ──► rechecking ──► resolved
   └──────────────────► escalated
```

- `active`：发现了，正在观察/诊断；
- `rechecking`：给过建议或动作，等结果；
- `resolved`：证据显示已恢复（**自动关**，不靠人点）；
- `escalated`：同一件事反复出现或恶化，需要人。

同一对象、同类症状在活跃期间更新同一条；恢复后再次出现则重新打开。
**去重靠库，不靠进程内的 `Set`**——现在的 `reported` 集合重启就失忆。

## 3. 能力边界

### 3.1 自动做

- 读库、算候选、调模型、写 incident、给自己记用量；
- 白名单动作（全部**可逆、幂等、先留痕**）：
  - 重连明确失效的外部连接；
  - 重跑健康检查；
  - 对已有恢复语义的基础设施动作发起恢复请求。

### 3.2 只能建议

- 重投任务、重跑失败任务、取消运行——都要人点头。
  `retryable` 现在的语义就是"可以重试"，**不是"自动重试"**；自动重投要先有幂等设计。

### 3.3 永远不做

- 杀任务（P6：一个马上要成功的运行不该被一个数字或一次误判掐掉）；
- 改验收结果 / 交付状态 / 任务归属；
- 把模型对话历史写进业务库；
- 预算封顶（只记账不封顶，`09-worker-spec.md` §3.8）。

---

## 4. 与其它层的契约

| 对方 | 契约 |
|---|---|
| **Worker** | Watchdog 只读 `task` / `task_trace` / `report`；不参与任务执行、不发指令给执行体 |
| **Router** | 不共享会话、不消费事件队列；故障通过 `system_event` 单向流向 Watchdog |
| **主进程** | 唯一的动手通道是窄 IPC（带 incident id + 幂等键 + 证据）；主进程不可达时只记待办 |
| **人** | 一个入口可以问它"这条任务为什么停住"；改规则要确认、要版本、要能回退 |

## 5. 分期

| 阶段 | 内容 | 交付判据 |
|---|---|---|
| **W0** | 本文档；进程/会话边界与 IPC 契约定稿 | 能回答"主进程卡住 / 崩了 / 应用退出"三种情况下它分别能做什么 |
| **W1** | 心跳 + `system_event` 落库，替代 `console` | 关键故障可按时间与对象查；能区分正常退出与异常退出 |
| **W2** | 独立子进程 + 独立 Session 骨架（只读） | 主进程事件循环被堵住时，它仍能读到状态并留下 incident |
| **W3** | `incident` 状态机与复查 | 恢复自动关、复发能再开、重启不失忆 |
| **W4** | 程序层候选改读 `task_trace` | 「改一行再跑还是失败」能判出来；无候选不花 token |
| **W5** | 模型语义诊断（进展/绕圈/偏离/证据不足） | 结论必须引用证据；不直接改任务终态 |
| **W6** | 白名单动作 + IPC 执行 + 回滚 | 重复请求不重复执行；失败不假装成已修复 |
| **W7** | 人的入口与规则管理 | 能被问、能解释；改规则要确认与审计 |
| **W8** | 打包、崩溃恢复、睡眠唤醒、版本升级 | 子进程崩了不拖垮主应用，重启后能接上 |

### W1 已落地

- `V47`：`system_heartbeat` / `system_event`；
- `data/systemEventRepository.ts`：`record` / `recordSafely` / `listRecent` / `listOpen` /
  `markHandled` / `beat` / `readHeartbeat` / `uncleanExit`；
- 主进程每 15 秒写一次心跳，退出前置 `stopping`；
  **`app.exit()`（探针与异常退出路径）不触发 `before-quit`**，所以另挂了一条
  `process.on('exit')` 同步写——否则每跑一次探针都会伪造一条"上次没正常退出"；
- 启动时若发现上一轮心跳仍是 `running`（实例不同），记一条 `process.unclean_exit`；
  判据只看状态与实例，**不看时间**：关了几天再打开说明不了任何事；
- 首批接入的故障点：Router 交给会话失败、任务恢复失败、任务运行失败、
  MCP 服务器连不上。

### W2 已落地

- `electron.vite.config.ts` 增加第二个 main 入口：`out/main/watchdog.js`；
- `watchdog/child.ts`：utilityProcess 入口。开两条连接（业务库**只读**、自己的库读写）、
  按间隔体检、把结果报给父进程；
- `watchdog/store.ts`：自己的库（`watchdog_finding` / `watchdog_tick`）。
  **去重落在库里**（部分唯一索引 `WHERE active = 1`），不落在内存的 `Set` 里；
- `watchdog/host.ts`：`start` / `whenReady` / `ping` / `stop`。子进程意外退出记一条
  `watchdog.exited` 并按退避重启（W8 补上）。
- `index.ts`：非无头启动时拉起，退出时先停；探针 `OPC_WATCHDOG_PROBE=1`。

实测（`WATCHDOG_PROBE`）：

```
主进程忙等 3 秒：子进程的 tick 从 606075 推进到 608082，activeFindings 照常
tickAdvancedWhileBlocked: true
```

把阈值临时调成 1 毫秒后，同一份库里出现**恰好一条** `main_unresponsive`
（多轮 tick 只更新同一条）——这就是"主进程卡住时证据还在"的第一个实物。

**这一版有意没做的两件事**（都记在这里，不留给读者猜）：

1. **模型会话**：W2 的骨架里没有 pi harness。语义判断到 W5 才接；最初是
   "子进程出题、主进程调用"，后来补齐成**子进程自己调用**（见 W5 与 §8）——
   凭据经 IPC 交付、只在内存，主进程仍不参与调用。
2. ~~旧的程序层 Watchdog 还在跑~~ —— W4 已删除，见下。

实测（真实库）：升级到 47、心跳落库、正常退出写 `stopping`；第二次启动不再重复记
`unclean_exit`——去重靠的是状态本身，不是内存里的一个标记。

### W3 已落地

**事实源**：incident 住在子进程自己的库（`watchdog_finding`），因为状态机必须在
主进程卡住时继续推进。业务库里的 `watchdog_incident`（V48）是**镜像**，由父进程按
每轮 `tick` 刷新，给 Router 与界面读——镜像可以丢，下一轮写平。

```
active ──(2 分钟还没好)──► rechecking ──(15 分钟还没好)──► escalated
   └──────────────────(条件消失)──────────────────────────► resolved
```

- **只升不降**：已经 escalated 的不会因为"又变年轻了"退回 rechecking；
- **恢复自动关**：条件消失就 `resolve`，不需要人点；
- **复发开新行**：关掉的行保留，再出现时新建一条并 `reopen_count + 1`——
  那两次不是同一件事，但它们是同一类事；
- 唯一索引 `WHERE active = 1` 保证同一症状只有一条活跃记录。

实测（同一份库，三种情况）：

| 场景 | 结果 |
|---|---|
| 阈值 1 毫秒 | `main_unresponsive` 立刻进 `escalated`，镜像同步为 `escalated` |
| 下一轮心跳正常 | `activeFindings` 归零、`mirror: []`、子进程库里那行变 `resolved` |
| 再次触发 | 新开一行，`reopen_count = 1`（两条并存：一条 resolved，一条 active） |

**这一版有意没做**：镜像只 upsert、不删除；把"这一页里没提到"解释成"已恢复"是
编造，只有子进程明确说 resolved 才算。界面入口留到 W7。

### W4 已落地

判据从 `task.steps` 换到 `task_trace`（`watchdog/candidates.ts`）：

| 规则 | 判据 | 为什么以前判不出来 |
|---|---|---|
| `repeat_failure` | 同一 `(工具, 参数摘要)` 在最近 20 步里 `ok=0` 出现 ≥3 次 | 旧规则数的是**句子**；「改一行再跑」每一步的文字都不一样，而命令和失败是一样的 |
| `no_progress` | 最后一条 trace（没有则 `started_at`）距今 >30 分钟，且任务仍 `running` | 旧的看 `updated_at`，而它会因为与进展无关的状态重写被刷新 |

两条规则不会同时开：判出打转就不判停滞——它们是同一个问题的两种描述，同时开
两条 incident 只会让人看两遍。

**关闭条件也是判据**：这一轮没再判出来的任务级发现会被 `resolve`；但只在
"这一轮看全了"（运行中任务少于一页）时才关——没看到不等于不存在。

旧的 `watchdog/watchdog.ts`（主进程 `setInterval` + `steps` 重复文本）已删除。
它唯一的用户可见出口由 incident 升级接住：一条 incident 变成 `escalated` 时，
在它所属的线上放一条 `decide`。判据是**状态迁移**（镜像里记录的前一状态），
不是内存里的"报过了"。

实测（隔离的临时库，直接跑子进程）：

```
repeat_failure  t1  「同一个动作失败了 3 次（bash node --check server.js）」
                    detail: { attempts: 3, seqs: [2,4,6], window: 6 }
no_progress     t2  「已经 40 分钟没有任何新动作」
```

第一条正是旧规则抓不到的形状：三次失败之间夹着 read / write，**每一步的文本都不同**。

### W5 已落地

**判断在子进程里做**（补齐后）：主进程只负责**解密**与**授权**——把"一个 provider
+ 一个模型 + 一把钥匙"通过 IPC 交过去，钥匙只存在子进程内存里，不进环境变量、
不写盘、不进日志。之后出题、调用、解析、落库全在子进程完成。

| 谁 | 做什么 |
|---|---|
| 主进程 | 解析目标模型、解密 key、`configure-model` 一发送；不参与调用 |
| 子进程 | 挑证据（目标 + 规则 + 最近 12 步动作）→ 调用 → 解析 → 落 verdict |
| 兜底 | 只有 OAuth（没有静态 key）或本地调用失败时，才回主进程代判，并记 `judged_by=parent` |

**为什么值得多这一层**：判断原本要绕回主进程，于是"主进程卡住"时语义层也停。
现在它和发现、记录、状态机一样活在子进程里——这才是"主进程之外"。

**两个只有真跑才会暴露的坑**（都已经写进代码注释）：

1. 子进程的 `fetch` 默认不读代理变量。应用的代理是环境变量形式传下来的，
   所以 fork 时补一句 `NODE_USE_ENV_PROXY=1`，否则判断会被直连失败逼回主进程。
2. pi 的模型描述必须带 `provider`（以及 `input`/`cost`）。少一个 `provider`，
   `complete()` 就报 `Unknown provider: undefined`，表现为"模型返回空文本"。

**两条必须自己管住的时限**（复核时补上）：

- 一次模型调用 2 分钟没回来就放弃这一次，**不假设 provider 支持 AbortSignal**；
- `pendingJudge` / `pendingAction` 是单飞的，3 分钟 / 12 分钟还没结果就自己放掉。
  没有这一层，一条永不返回的请求会让语义层或动作层永久停摆，而日志里只有"安静"。
  判断超时会记一次 `judged_at`（否则放掉之后立刻重试，模型不可用就变成重试风暴）；
  动作的上限故意比账本的 5 分钟认领窗口长，两边不会互相打断。

**改配置要立刻生效**：`configure-model` 不只在 `ready` 时发。设置页换模型、
换 provider 的钥匙、改默认 LLM，都会触发 `WatchdogHost.refreshModel()` 重发一遍——
否则界面显示 B、子进程还拿着 A 的钥匙，直到下一次重启。

**结论只有五种**，且 `insufficient_evidence` 是一个合法答案——逼模型给结论只会多一种误判：

```
progressing / stalled / looping / deviating / insufficient_evidence
```

**花销的闸门**是两件事叠起来的：一次只问一条；同一件事 30 分钟冷却（`judged_at` 落库，
重启之后也记得判过）。判断失败同样记冷却，否则模型不可用时每轮都会重试。

**升级条件**：结论是 `stalled / looping / deviating` **且**置信度 ≥ 0.6，才把 incident
推到 `escalated`（那一条会变成线上的一条 `decide`）。低置信度只落记录，不打扰人。

**踩到的一个坑**：这个 provider 不转发 `systemPrompt`，模型把指令当空气，回了 1000 多字的
修复建议。修法是**把指令同时写进 user 消息**——不能假设 system 那一层一定到得了。
提示词与解析因此被抽到 `watchdog/prompt.ts`，两条路共用同一份。

实测（真模型，端到端）：

```
子进程：repeat_failure（bash node --check server.js 失败 3 次）
   ↓ 子进程自己调用（judged_by=child）
verdict=looping, confidence=0.82
   ↓ 落库
incident → escalated；镜像同步
```

第二次启动时 `judged` 直接是 1——冷却在库里，不靠内存。

### W6 已落地

**能力边界写进了类型**：`ActionName` 只有 `'mcp.reconnect'` 一个值。加一条新动作必须先在
协议里写清楚名字，顺手拼一个字符串是通不过类型检查的。`kill`、`retry_task`、`cancel`
不在里面，也不该在里面——那三件事要么违反 P6，要么需要人拍板。

**三件事按顺序做，缺一步都不算"修过"**：

1. **认领**（主进程，`watchdog_action` 表）：`UNIQUE (incident_id, action)`。
   重复请求直接返回"已执行过"——不是靠子进程记得，是靠库。
2. **执行**（主进程）：`mcp.reconnect` = 断开共享连接 + 让执行体 harness 失效，
   下一个任务重新挂载。幂等，最坏结果是"还是连不上"。
3. **回写**：成功 `done`、失败 `failed` + 原因、不在白名单 `refused`。
   **失败不改 incident 状态**——动作没成功只说明这次没修好，问题还在。

**incident 从哪来**：MCP 连不上以前只在 `system_event` 里躺着。现在子进程把
"还没人处理的系统故障"变成 incident（主体、证据、状态齐全），这也是第一个
真正可以被动作修的对象。

实测（同一个临时库跑两次）：

```
第 1 次：actions=[{ action:'mcp.reconnect', status:'done' }]
第 2 次：子进程记录 action_result = "已执行：这条动作已经执行过（幂等跳过）"
        账本里仍然只有 1 行 —— 幂等是库给的，不是记忆给的
```

**已知缺口（说清楚，不藏着）**：重连成功后没有人去验证 MCP 是否真的恢复，所以那条
incident 会停在 `active`，等下一次挂载成功（或人处理掉 `system_event`）才关。
"重连发出去了"不等于"连上了"，把它当已解决就是撒谎。

### W7 已落地

设置 → **进展监督**（`WatchdogPage`）。三块，都是只读或"明确保存"：

| 块 | 做什么 | 边界 |
|---|---|---|
| **正在发生的事** | incident 列表（状态、对象、摘要、复发次数） | 每分钟刷新；状态由子进程推，界面不改 |
| **问它一句** | 用 incident + 动作账本 + 未处理故障回答 | 只答证据里有的；每条结论挂 `[i:…]`/`[a:…]`/`[e:…]`；不知道就说不知道 |
| **它最近做过什么** | `watchdog_action` 账本 | 审计用，不可编辑 |
| **规则** | 总开关 / 空闲判定 / 重复次数 / 心跳阈值 / 升级时长 / 判断间隔 | 保存 = 确认；**回退是回到上一版，不是恢复默认** |

**规则存在 `app_setting`，子进程每轮现读**：保存之后下一轮就按新值走，不需要重启应用，
也不需要重启它自己。总开关关掉之后它仍然体检、仍然推进状态（证据不能因为"别吵我"就断），
只是不再报警、不再花模型调用、不再请求动作。

实测：把 `enabled:false` 写进临时库后跑同一套探针，**没有产生新的 incident**——
开关是有效的，而不是只改了一个界面字段。

`ask` 的三条自我约束写在 `watchdog/ask.ts` 顶部：证据之外不回答、必须引用编号、只读。
它不能改任何东西：要改规则去设置页，要修走 W6 的白名单。

### W8 已落地

| 事项 | 做法 |
|---|---|
| **崩溃重启** | 退避 1s → 5s → 30s；10 分钟内最多 3 次；超限记 `watchdog.restart_given_up` 并停手 |
| **父进程这一侧的存活检查** | 每分钟 `ping` 一次；连续无回应记 `watchdog.unresponsive`，恢复后可再记 |
| **睡眠/唤醒** | 用它**自己的**上一轮间隔判断：这一轮距上一轮远超正常间隔，说明整机被挂起，这一轮不判心跳 |
| **打包** | `electron-builder.yml` 把 `out/main/watchdog.js` 加进 `asarUnpack`；`entryPath()` 先找 asar 内、再找 `app.asar.unpacked` |

**顺带收紧了 incident 的语义**：只有"会自愈的条件"才转成 incident（目前是 MCP 断连）。
`process.unclean_exit`、`watchdog.exited`、`router.session_failed` 是**已经发生过一次的事实**，
没有"是否恢复"可言——它们留在 `system_event` 里，不再变成永远关不掉的 incident。
非条件类的旧条目会在下一轮被关掉。

实测（探针里主动杀死子进程）：

```
pids: [19468, 35640]           ← 换了一个进程
restarted: true
tickAdvancedWhileBlocked: true
mirror: []                     ← 没有留下关不掉的条目
exit=0
```

**没有验证到的**：真实睡眠/唤醒（需要挂起整机）与打包后的产物（需要跑一次
`electron-builder`）。前者的判据是"自己的间隔"，后者的兜底是两条路径都试——
两项都在这里写明，不假装跑过。

## 6. 不变量

1. **判断可以错，动作不能不可逆。**
2. **先程序筛，再模型判**；没有候选时零调用。
3. **结论必须引用证据**（event id / trace seq / task id），也可以回答"证据不足"。
4. **它不能决定一个任务完成、失败或取消。**
5. **每次状态变化与动作请求都落库**，可复查、可审计。
6. **写库失败不阻塞主进程**；IPC 不通时不假装修好了。
7. **不设预算上限**：用量照记，值不值由人看数字判断。

---

## 7. 不做

| 不做 | 理由 |
|---|---|
| 应用退出后继续监督 | 那是系统服务；桌面应用的产品定位没变，单独立项 |
| 自动重投 / 自动重跑失败任务 | 幂等与副作用语义还没设计；先做"能判"，再做"能重" |
| 杀任务 | P6 |
| 把 Watchdog 的对话历史塞进业务库 | 两种生命周期，混在一起备份与清理都会变难 |
| 预算封顶 | 与 `09-worker-spec.md` §3.8 一致：只记账 |

## 8. 审查修复（本轮）

审查发现的问题与处理：

| 问题 | 处理 |
|---|---|
| 动作认领把 `pending`/`failed` 当成"已执行" | 认领改成五态：`claimed / done / refused / in_flight / exhausted`；pending 超过 5 分钟视为执行者已死，可重新认领；同一动作最多 3 次 |
| 通知失败后永久静音 | 镜像新增 `announced_at` / `announce_attempts`：**升级 ≠ 已通知**，失败下轮重试，5 次为止 |
| 只扫最旧的 20 个运行任务，后者长期饿死 | 游标分页（`watchdog_cursor`，跨重启保留）；**是否关闭一条发现按"这个任务这一轮被没被看到"判**，不再按"扫没扫到队尾"（见下） |
| 主进程断开时子进程立刻退出 | 改为**孤儿宽限**（默认 2 分钟）：继续记录、不再请求判断与动作，窗口到了自己退出 |
| `summary` 可能带出凭据 | 新增 `scrubSecrets`（`data/scrub.ts`），`system_event` 与 `watchdog_finding` 的摘要/detail 都过一遍（Bearer/token/URL 凭据/`key=…`） |
| 回答可以伪造证据编号 | 只保留确实存在于本次证据的引用，其余从回答里剔除并计数；编号从 4 位加长到 8 位 |
| 问答看不到 trace 细节 | incident 镜像带 `detail`，问答把它一起喂给模型 |
| 规则保存/回退不是事务 | 包进 SQLite 事务；另存最近 10 版用于审计（回退仍只回上一版） |
| 设置页缺 `recheck` / 动作冷却 | 已补上两个字段 |
| 子进程起不来时不重启 | `spawn_failed` 也走退避重启 |
| 业务库打不开仍报 ready | `ready.businessDbOpen === false` 时 `whenReady` 返回 false 并记一条故障 |
| 没有独立模型配置 | 新增 `watchdog.model`（设置页可选），没配才退回默认 LLM |
| 判断在主进程执行，主进程卡住时语义层也停 | 判断搬进子进程：主进程只解密与授权，钥匙经 IPC 交付、只在内存；OAuth-only 才退回代判 |

### 8.1 第二轮复核（本次）

上一次的修复有一半是对的，另一半**在真实形状下不成立**。逐条复核后的结果：

| 复核发现 | 处理 |
|---|---|
| 游标分页后，"到队尾才关"被实现成"这一页没看见就关"：任务多于一页时，上一页还在打转的发现每轮都被关掉、下一轮再开一条 | 改为按任务判：**这一轮看过的**任务没再成立才关；没在本页的，只有"已经不在 `running`"才关 |
| 升级通知的"送到了"是假的：`onEscalated` 返回 `void`，而它对进程级事件、没有 `thread_id` 的任务直接 `return`——宿主照样写 `announced_at` | `onEscalated` 必须返回 `boolean`；只有 `true` 才 `markAnnounced`，其余记一次尝试（5 次封顶） |
| "正在执行"被回报成 `ok: true`，子进程记成"已执行" | `in_flight` 回 `ok: false`：它**没有**被执行 |
| 判断/动作请求没有时限：一条永不返回的请求会永久堵住后面所有判断或动作 | 子进程侧 3 分钟 / 12 分钟超时释放；单次模型调用 2 分钟超时 |
| 设置页换了模型，子进程还在用旧的 provider 与钥匙（`configure-model` 只在 `ready` 发） | 新增 `WatchdogHost.refreshModel()`；`watchdog:setModel`、`setKey`、`saveProvider`、`removeProvider`、默认 LLM 变更都会触发 |
| 问答里动作的引用编号其实是 incidentId 前 8 位（`padEnd` 在长串上是空操作），同一 incident 的多条动作会共用一个编号 | 改成对 `incidentId + action` 做 FNV-1a，取 8 位十六进制 |
| Watchdog 自己的摘要没有脱敏（只有 `system_event` 做了） | `scrubSecrets` 抽到 `data/scrub.ts`，`WatchdogStore.raise` / `setVerdict` 也过一遍 |

**实测（25 个运行中任务、每个都连续失败 3 次，同一份临时库）**：

```
修复前：出现发现的 25 个任务里，20 个被反复关/开
        每个任务留下 8 条记录、全部 resolved（同一条被关了又开 7 次）—— 一轮驱动一代
修复后：25 个任务各 1 条，0 个被反复关/开
        把其中一个任务改成 done 再跑：它的发现 resolved=1/1，其余 24 个 0 误关
```

**实测（进程级升级，`staleMainMs=1ms`）**：

```
镜像：state=escalated, announced_at=null, announce_attempts=5
```

试满 5 次就停手，并且**没有**把"没送出去"写成"已通知"。进程级事件目前没有线
可以说话，这条记录就是它的去处——等 §7 的入口。

**仍然存在的偏差**（不掩盖）：

1. **没有 pi durable 会话历史**：判断已经搬进子进程（模型调用、凭据、解析都在那边），
   但每次判断只看**当下这一份证据**，没有跨轮次的对话记忆。要做到"它记得自己昨天的
   判断"，需要一个真正的 durable session——那是另一件事，不靠加一个字段解决。
   OAuth-only 的 provider 仍然退回主进程代判（记 `judged_by=parent`）。
2. **应用退出即停**：按 §0 的范围，常驻是另一个项目。
3. **动作只到"发出重连"**：没有验证 MCP 是否真的恢复。
4. **打包产物与真实睡眠未跑过**。
