## 0. 原文对 Worker 层的全部要求，逐句

原文这一节只有两段，但每一句都在约束一件事。把"约束的是什么"和"我们现在在哪"分开列，
才看得出哪一条是缺口、哪一条只是措辞。

| 原文 | 它真正约束的 | 我们 |
|---|---|---|
| 「各个 Worker 彼此上下文隔离」 | 隔离的**粒度**：一个任务一份上下文，不是一个线程，也不是一个人 | ✅ 每个执行体一份 `agents/<workerId>.sqlite`；每个任务一个 workspace |
| 「挂载完整的执行工具」 | 工具集是**执行体的属性**，不是全局的 | ✅ `toolSlots` / `buildRegistry`，条件（缺 key、缺模型）在装配处判 |
| 「在独立上下文中专注完成**单一任务**」 | 同一时刻只推进一件事 | ✅ `work/ownerQueue.ts`（串行是正确性，不是调度优化） |
| 「通常需要配置**能力最强的模型**」 | 模型跟着执行体走，且与 Router 不同档 | ⚠️ 执行体的模型是它自己的属性（创建时钉住）——但 Router **没有单独的轻量档**，两者取同一个默认 LLM |
| 「Worker **不会直接与人类交互**，其推理过程与工具调用不会直接输出到外部信道」 | 没有聊天出口 | ✅ 执行体没有 `reply_to_user`；`OPC_CHAT_PERSIST_PROBE` 断言它没开过口 |
| 「而是向 Router 层**汇报状态**，由 Router 层统一向用户回复」 | 汇报是它唯一的外向通道 | ⚠️ 只有**终局**汇报（`reportToThread`），中途中没有通道 → **E3** |

| 「少数跨任务协同则由 Router 层中转」 | 跨线只能经过 Router | ✅ `decompose`（子任务各自成线、各自验收、Router 可见） |
| 「每个 Worker Session 在内部**也不必局限于单个会话**：可以再创建 Subagent，也可以本身就是一个 Agent Team，对 Router 保持透明」 | 执行体内部可以再隔离一层 | ❌ 没有。`decompose` 拆的是**交付物**，不是**思考** → **E2** |
| §3.2「若新事件**超出了当前任务的范围**，Worker 也可取消订阅或交回 Router 层重新分派」 | 执行体能主动退出，而不是硬干或失败 | ❌ → **E3** |
| §3.3「每次召回的对象均**内联下一跳关联对象的 ID**」 | 执行体看到的上下文也该是"ID + 摘要 + 按需展开" | ❌ 执行体只看到 Router 的**转述**，且没有读库工具 → **E1** |
| §3.4 投机执行 | 后台先试，有价值才交付 | ❌ → **E4**（只拿一半，见那一节） |
| §4.1 异步 ReAct Loop（`start()`/`stop()`） | 工具级不阻塞 | ❌ **判断不做**，理由见 §11 |
| §5 计算/状态/环境分离、端侧 daemon | 执行环境留在原地 | ❌ **判断不做**（本地优先，三者天然合一） |
| §6 Watchdog 判断「Worker **是否有实质进展、方向是否偏离整体目标**」 | 执行体必须留下可供判断的痕迹 | ⚠️ 程序层有（转圈/停滞/孤儿）；语义层**没有参照物**——执行体从不声明它打算怎么干 |

三处 ⚠️ 里，两处是缺口（模型档位、汇报通道），一处是被上游卡的（Watchdog 缺参照物，等 E2/E1
把"执行体的意图"变成数据才谈得上判偏离）。

## 1. 第一性原理：执行体是什么

先问一个问题：既然 Router 也有工具，为什么还要单独一层？

因为**一个 ReAct Loop 一次只能推进一件事，而它的上下文会被这件事的全部细节淹没**。
这两件事都不随模型变强而消失：串行是循环的形状，混杂是窗口的物理大小。

所以执行体 = **一个目标 + 一份隔离的上下文 + 一整套工具 + 一条外向通道**。
少了任何一个，它就不再是执行体：

- 少了目标 → 它是聊天窗口；
- 少了隔离 → 一次失败的工具调用会污染同一份上下文里的下一件事；
- 少了工具 → 它是 Router 的副本，多花一份钱；
- 少了那条通道 → 它干的事没人知道。

### 五条公理

**E-A1 执行体的产物是"可判定的改变"，不是"一段话"。**
它交出的东西必须能被系统判对错（退出码、verdict、文件是否真的在）。这就是为什么
`produce → verify` 是一个状态机而不是一次生成：**"模型说它做完了"不构成完成**。
推论：没有可执行验收条件的任务，结论只能是"需要人看一眼"，不能是"通过"（`acceptanceGate.ts`
的 `isUnverified`）。

**E-A2 隔离是它存在的理由，不是副作用。**
隔离的粒度是**任务**。两个人共享一份会话会互相读到对方的事；两个任务共享一份会话会互相读到
对方的失败。所以同一个执行体在同一时刻只跑一个任务，一个任务一个 workspace。

**E-A3 执行体不与人对话。**
一旦它能开口，它就会开始解释自己为什么没干完——而解释是廉价的，干活是贵的。并发时多张嘴
还意味着你会同时收到五条自相矛盾的进度。**外向的话只有 Router 说。**

**E-A4 执行体之间不点对点通信。**
它们需要知道的事，共享事件流已经提供了：同一份 Thread 上的新事件按序到达每个订阅者。点对点
需要重新回答"谁先、死了怎么办、丢了怎么补"——而这套答案在事件流里已经有了。

**E-A5 成本必须归因到线。**
执行体是最贵的一层（最强模型 + 大量工具调用）。账必须记在"这条线"上，不是记在"系统"上，
否则"这件事值不值"永远没有答案。

### 四条硬规则（由公理推出，不许违反）

1. **一个执行体，同一时刻只跑一个任务。** 不是排队优化：两轮 run 并发写同一份 sqlite 会毒化
   会话，之后这个执行体的每一次运行都会失败（`ownerQueue.ts` 的头注释记着这一次事故）。
2. **结束必须可判定。** 没有闸门就说"验不了"，不假装通过。
3. **可观测状态必须落库。** 步骤、产物、验收、token —— 因为 Watchdog 在**主系统之外**，
   它读不到内存里的任何东西。
4. **失败必须能读出一句人话。** 模型不可用、缺验收条件、超预算、卡住，都要落成原因；
   「卡在进行中」是账本最坏的一种状态。

## 2. 能力的四层

把上面这些摊开，执行体需要的能力分四层。分层的依据是**它决定了什么**，不是代码在哪：

```
① 执行      workspace · 工具集 · 模型 · 预算 · 串行
             决定了：它能不能把事做完
② 上下文    注入什么 · 按需读什么
             决定了：它做的是不是对的那件事
③ 汇报      终局怎么说 · 中途怎么说 · 什么时候闭嘴 · 什么时候退出
             决定了：它做的事有没有人知道
④ 自我延伸  子代理 · 投机
             决定了：它一次能处理多复杂的事
```

①已经对齐了。②③④是这份文档要设计的东西。

## 4. E1 它看不见原始证据

### 现象

`workDispatch.ts` 建任务时：

```
brief           = goal          ← Router 写的一段话
deliverableSpec = goal          ← 同一段话
```

执行体的提示词里因此只有 Router 的**转述**。原文那句话是 Router 的 `open_line_of_work`
自己写的：「写清目标和验收标准，**执行体只看得到这些**」——它现在是字面意义上的事实。

三个后果，一个比一个难查：

1. **有损**。用户原话里的端口、路径、报错原文，在转述里会被压缩掉。执行体于是"按要求做了"，
   做的是转述后的那个要求。
2. **不可自纠**。Router 把 A 问题理解成 B 问题时，执行体是唯一有机会发现的人——但它看不到 A。
3. **没有下一跳**。原文 §3.3 的链式召回靠"注入时内联关联对象的 ID"实现。执行体手里没有 ID，
   所以既回不到事件，也回不到这条线之前发生过什么。

### 决定

执行体拿到的是 **ID + 摘要**，全文留在库里，要用再取。

1. `WorkTask.records`：`{ kind: 'event'|'report'|'task'|'thread'; id; title; excerpt }[]`。
   由**程序**在派活时填（`workDispatch`），Router 不用管——直通那条路（不经过模型）也自动有。
2. 执行体新增只读工具 **`recall`**，与 Router 的同名同义，只是作用域收窄：它只能取自己这条线
   和这条线上的任务/事件/汇报。取全文时**分页**，和 Router 的读侧限长是同一条理由——把全文
   倒回上下文等于把 spill 白做了。
3. 预算**复用同一个函数**：`router/inline.ts` 的 `perItemBudget` / `spillText`。两层看到同一段
   文字，是 `05-router-real.md` §5 已经立下的原则；执行体这一侧之前没有遵守，因为它根本没被
   spill 过。
4. 提示词里单独一段，排在「交付物」之后、「要求」之前：

```
任务：…
说明：…
交付物：…

这件事的原始记录（要用全文就 recall <id>）：
- event ev-3f2a · 群聊：能不能把健康检查的端口改成 8081
  …（略去 12 行）… 共 40 行 / 1832 字
```

### 为什么不是"把事件全文拼进提示词"

因为主战场是 workspace 里的文件，事件正文往往只是引子。20 条事件全文会挤掉它真正需要的窗口，
而 §3.3 那句话是硬的：**浪费上下文窗口，就是浪费模型的智能**。

### 为什么不是"让 Router 转述得更详细"

那是在**错误的层**上修一个保真度问题：Router 的转述再详细，也是一次压缩，而且它压缩时不知道
执行体后面会需要什么。给 ID 是唯一不需要预知未来的做法。

### 验收

- 一条带具体端口与路径的事件 → 派出去之后，执行体的提示词里**逐字**保留那些字面。
- `recall ev-…` 能取到全文；取别的线的事件被拒（作用域）。
- 40 条长事件合起来不超过预算 + 固定开销——**性能断言**，不是格式断言（对齐 `inline.test.ts`
  那条）。

## 5. E2 拆思考：子代理

### 现象

一个任务里常有"先查清三件事，再决定怎么写"。现在执行体只有一份上下文：每查一件事，那一整段
工具输出就永久留在窗口里。查到第三件时，前两件的无关细节已经把注意力稀释掉了——这正是原文
§2 说的"多任务的中间细节混杂在一起也会影响完成效果"，只不过它在**一个任务内部**就发生了。

`decompose` 救不了这个：它拆的是**交付物**（子任务各自成线、各自验收、各自向 Router 汇报）。
而这里要拆的是**思考**：没有独立交付物，结论回到父。

| | `decompose` | `investigate`（本节） |
|---|---|---|
| 拆什么 | 交付物 | 思考 |
| 在库里是什么 | 新任务 + 新线（可选） | **什么都不是**，一段返回 |
| 谁验收 | 各自的闸门 | 没有闸门，父自己判断信不信 |
| Router 看得见吗 | 看得见（汇报） | 透明，只留步骤记录 |
| 账记在谁头上 | 各自的任务 | **父任务** |

### 决定：一个工具，八条限制

```
investigate(question, expects) → { answer, read: string[], written: string[] }
```

1. **深度 1**。子代理不能再开子代理。为什么不无限：这条链上没有任何一层在收敛，成本失控而收益
   在第一层就拿到了。
2. **一次任务最多 3 个，且串行**。为什么串行：它们共享一个 workspace，两个并行写会互相覆盖；
   而真正需要并行的是**线之间**，不是"一个任务内部的思考之间"。
3. **只读 + 自己的 scratch 子目录**，不许写 workspace 根。为什么：验收只认根下的产物，父是唯一
   对"我交出的是什么"负责的人。子代理能随便写，父就失去了确定性——而它还要拿这个去面对闸门。
4. **返回结论 + 它读过/写过的相对路径，不返回全文**。同 §3.3：给引用，不给全文。
5. **账记到父任务**。为什么：账目里不该出现"没有任务的支出"；线级预算才说得上"这件事值不值"。
6. **对 Router 透明**：不建线、不产生汇报。**但步骤要记进父任务的步骤流**，带 `[查 n]` 前缀。
   为什么透明但可见：Router 不需要知道它的存在（那是细节），但 Watchdog 和你需要——可观测是硬规则。
7. **它继承约束，不继承历史**：拿到子问题、父任务的交付物规格、工作目录、**常驻约束与做事规矩**
   （用户对输出的要求对子输出同样成立），不拿父的对话历史。
8. **失败不传染**：子代理失败是**一次返回值**（「没查出来，原因是…」），不是父任务失败。为什么：
   父还可以自己查或换路子；把一次可恢复的探索升格成一次返工，是拿最贵的单位（尝试次数）去付最便宜的账。

### 为什么不做成"一线多执行体"

那已经是 `decompose` 了，而且它解决的是另一个问题：一件大事其实是三件小事。子代理要解决的是
**一件事的推理深度**。混在一起会得到一个既贵又慢的东西：每条线都变成多执行体，Router 要为每个
执行体各写一次目标。

### 验收

深度上限 / 串行 / 只读（试图写根被拒）/ 合账（父任务的 tokens 增加、没有新任务行）/ 步骤可见 /
失败不传染 —— 六条用例，一条一个限制。

## 6. E3 它只有终局的嘴

### 现象

执行体的中途状态只进 `task.steps`（界面看得见），`report` 表里只有终局那一条。于是它遇到需要
更大视野的决定时，只有两条路：

| 它其实想说 | 现在它只能 | 代价 |
|---|---|---|
| 「两个方案，A 快 B 稳，你要哪个」 | 猜一个 | 跑完一个你不想要的东西 |
| 「缺验收标准，我不知道什么算做完」 | 失败 | 一次尝试 + 一笔钱 + Router 一次复盘 |
| 「这条线不该由我做（目标变了/缺权限）」 | 硬干或失败 | 同上，而且线还占着 |

原文对 Worker 的要求是「向 Router 层**汇报状态**」——状态是过程性的，不只是终局的。

### 决定：两个工具，一条闸门

**`escalate`（请示）** —— 一句问题 + 你试过什么 + 你的建议 → `report(level: 'decide')`。

- **每个任务至多 1 次**。同一任务第二次降级为 `notify`。
  为什么限一次：一个执行体在同一件事上请示两次，说明它不该接这件事；而每请示一次，你就要放下手
  上的事一次。
- 它是**任务内的一条待办**，不是任务的一个状态：任务还在跑（等回答），状态机不动。

**`hand_back`（交回）** —— 退订 + 线回到 `open` + `report(decide, 原因)`。

- 为什么是工具而不是"让它失败"：失败要花一次尝试、还耗预算；**"不是我该做的"不是失败**，
  它是一次成功的判断。

**闸门：进度不进 Router。**

`task.steps` 里每一步都进 `report` 队列，Router 就变成日志消费者——这和 `07-memory.md` §21
里删掉的那条写入是同一个错误：**日志冒充汇报**。`05-router-real.md` §3.2 已经定过 Router 只接
收两种东西：没有归属的新事件，和要开口说的汇报。进度属于第一种的反面——它有归属，且不需要开口。

### 验收

- `escalate` → `report(decide)` 出现 → 下一轮进 Router 输入。
- 同一任务第二次 `escalate` 不是 `decide`。
- `hand_back` → `subscription` 里没有它了、线程回 `open`、汇报里写着原因。
- 一次正常的任务，`report` 表里**没有** progress 类的行（断言 count，不是断言"没有 decide"）。

## 7. E4 静默线

### 现象

原文 §3.4 的例子（群里有人反馈问题，先在后台复现并修复，确认找到简单方案才交付，否则全程安静）
是**两个动作**拼成的：提前跑 + 说完不说话。我们一个都没有。

### 决定：只做后一半，并说清为什么

`thread.speculative`（默认 0）。Router 的 `open_line_of_work` 多一个 `speculative` 参数。
规则只有一条：

> **这条线上的汇报永远不是 `decide`；闸门通过时升级到 `notify`，没通过就 `silent` 归档。**

为什么"永远不是 decide"：`decide` 的意思是「我要你放下手上的事」，而投机的前提恰恰是**这件事
还没有确定性价值**。

为什么不做前一半（用户没要求就提前跑）：那需要「后台有富余算力」这个前提。我们是单机、单个人
的机器，提前跑就是抢你自己的时间——`04-superagent-check.md` §1 的那条判断仍然成立。

所以 E4 的适用场景是：**Router 已经判断"这值得跑"，但"值不值得让你知道"还不确定**。例如群里
有人报了个错，Router 判断值得查，但查不通就不该打扰。这不是投机执行的全部，是它能被搬到单机上
的那一半，而且它几乎不花新代码——判据（闸门）和执行（任务）都是现成的。

一条必须有的护栏：静默线**必须有预算上限**（`thread.budget_tokens` 已有）。没有上限的静默线
是"花了钱你永远不知道"。

### 验收

- 静默线通过闸门 → 汇报 `notify`；没通过 → `silent` 且不进队列。
- 静默线上的 `escalate` **也不进 `decide`**（否则它就不是静默的了）——记 `notify`。
- 超过预算 → 收线并 `notify` 一次（"我试过了，不值得"也是一条结论）。

## 8. 一次交接：一条线上的第二个任务

### 现象

`harnessBrain.execute` 每个任务都 `createConversation`——**一个任务一份新会话**。所以一条线上的
第二个任务看不到第一个任务的过程，而记忆的写入判据（`07-memory.md` §21）又明确把过程记录排除在外。

原文里的 Worker 是"持续订阅这条 Thread 的会话"，它的连续性来自会话本身。我们这里没有。

### 决定：一任务一会话 + 一份结构化交接

不合并成一个长会话。理由是同一条局部性原理：一条线跑十次以后，前九次的失败日志和工具输出全在
窗口里，compaction 会先吃掉旧细节——而旧细节里恰恰有"上次为什么失败"。

所以开新任务时注入一段交接，**只放可推断的那一段**：

```
这条线上之前发生过（要细节就 recall task:<id>）：
- 第 1 次：写一个健康检查服务 · 通过 · 产出 server.js
- 第 2 次：端口改成 8081 · 未通过（退出码 1：EADDRINUSE）· 产出 server.js
```

四条规则：只取最近 3 条；每条一行；不含全文；老任务没有交接段时不报错（数据可以缺，代码不许崩）。

### 验收

第二个任务的提示词含交接段；交接段有字符上限（长标题不撑爆）；空历史时不出现空标题。

## 9. 生命周期

| 时刻 | 现在 | 该有的 |
|---|---|---|
| 这条线第一次派活 | `ensureWorker` 从模板复制一行 worker、订阅 | 一致（已对齐） |
| 线上再来一个事件 | 直通 → 同一个 worker 上排队（新任务） | 一致 |
| 线收线（`close_line` 或终态） | 退订 + `retireWorker` | 一致 |
| worker 退休之后 | `agents/<workerId>.sqlite` 留在盘上，永不回收 | 保留（删掉的东西没法恢复），但要有可见的"占多少" |
| 崩溃重启 | `resumeInterrupted` 接着跑 durable checkpoint | 一致 |

**不做自动 GC**：这是记忆那次给的教训——删掉的东西没法恢复。执行体的会话历史是"它当时为什么这么
干"的唯一证据，比它占的那几 MB 值钱。要的是**看得见的占用**，不是自动清理。

### 落到了哪

| 摘要生成（时间序、最多 8 条、按条数分摊预算） | `work/records.ts` 的 `buildRecords` |

一个细节值得记下：**记录不落库，每次 `produce` 现取**。派活时快照一份，会把"派活之后
才到的事件"漏掉——而直通那条路本来就意味着事件会一直在来。现取的代价是每次尝试多两条
`SELECT`，换来的是执行体看到的永远是此刻的这条线。

### 三个判断

1. **给 ID 而不是给全文。** 全文会挤掉 workspace 那个真正的主战场（§3.3：浪费窗口就是浪费
   智能）。摘要用 Router 那一侧的同一个 `spillText`，所以两层看到的是同一段文字——
   `05-router-real.md` §5 立过这条原则，执行体这侧之前根本没被 spill 过。
2. **记录是背景，不是要求。** 排在「交付物」之后、「要求」之前：放前面模型会以为那是任务
   本身，放后面会被读成附加约束。
3. **作用域由任务决定，不由模型决定。** `recall` 只能读自己这条线上的事件/汇报/任务；
   越界与"打错 id"回两句话——一句教它边界，一句让它别慌。

### 用例

`records.test.ts`（6 条）：短正文原样给、长正文取头尾并给出 recall 入口、时间升序、最多八条
取最近、**40 条长记录合起来不超预算**（性能断言）、空输入给空数组。

`harnessBrain.test.ts`（+3）：单独一段、段序（交付物 < 原始记录 < 要求）、多行摘要缩进、

没有在跑的任务不猜作用域、空 id 不查库。

`workThreadReport.test.ts`（+4）：真实事件 → 任务里出现「注入 1 条原始记录」，摘要里
**逐字**保留用户原话（`8081`）；顺着那个 id 取得到全文；别的线上的取不到；任务自己不
算背景。

## 13. E2 已落地：拆思考，不是拆交付物

### 落到了哪

| 东西 | 在哪 |
|---|---|
| 契约（请求 / 结论 / 提示词 / 读回 answer.md） | `work/subagent.ts` |
| 工具 + 三道闸门 | `work/investigateTool.ts` |
| 真的跑一次：独立存储、scratch 工作区、合账 | `workService.runSubagent` |
| 约束继承（常驻 / 做事规矩 / 工作台规定） | `workService.constraintsFor` |
| 用量差分的两件小算术（执行体与子代理共用） | `work/usage.ts` |

### 三个实现决定，和它们的理由

**① 子代理跑在另一份存储上（`<workerId>--sub.sqlite`），而不是同一个 harness 里。**

最初想的是"同一个 harness 里再开一个会话"——它是同一套工具、同一个模型，看起来更省。
放弃的理由有两条，第二条是硬的：上下文隔离是子代理存在的意义，共用一个会话库等于没隔离；
而且**工具调用在等另一轮 generation 时，同一个 harness 里的调度顺序是不确定的**。让一个
工具去等同一个调度器里的另一件活，是一个随时会变成"卡住十分钟"的设计。

代价照实说：每个执行体多一个 sqlite，同一份 registry 会被打开两次。

**② 深度 1 不是"把工具藏起来"，是"同一时刻只允许一个在跑"。**

模块级、按任务键的 `inFlight`。之所以不能是闭包状态：子代理的工具集是另一次
`buildRegistry` 的产物，闭包状态各算各的，深度就会变成 2。按任务键放在进程里，父挂着的时候
子代理再调它，得到的就是"已经有一个在查了"。

串行与深度是同一个开关——它们回答的是同一个问题：**这一层还能不能再分出去**。

**③ 只读是**执行出来的**，不是叮嘱出来的。**

沙箱的 seatbelt profile 是 `(allow default)` + `(deny file-write*)` + 只放行一个可写根。
所以给子代理的 `registerSandboxWorkspace` 是 scratch 目录：父任务的工作目录它**读得到**
（`allow default` 放行读）、**写不进去**（写只放行 scratch）。提示词里那句"那里只读"只是
让它少撞一次墙。**没有沙箱后端时这条不成立**——和执行体那一层是同一个边界，照实记在这里。

### 用例

`investigateTool.test.ts`（6 条）：拿回结论并合账、产出不算交付物（说清那些文件在哪）、
**串行/深度同一个开关**（一个在跑时第二个被拒，回来之后可以再派）、一个任务最多三次、
失败不传染（"你可以自己查"）、没有任务或问题太短都不派。

`subagent.test.ts`（5 条）：不是来交付的 + 结论写哪、两个绝对路径都给出且标明只读、
继承约束但不继承历史、不许再往下派、没有额外要求时不留空标题。

### 这一层之后

执行体的四层能力里，①②③都齐了。剩下的是 E3（中途请示与交回）和 E4（静默线）。

## 14. E3 已落地：它不再只有终局的那张嘴

### 两个工具，一条闸门

| | 做什么 | 关键约束 |
|---|---|---|
| `escalate` | 把"我定不了"投到线上 | **同一件事第二次不插队**（decide → notify） |
| `hand_back` | 这条线不该由我做：退订 + 线回 `open` + 留一条说明 | **不是失败**，不消耗尝试 |

闸门：**进度不进 Router**。`task.steps` 是给界面和 Watchdog 看的，`report` 是给 Router 和
人看的。两者的区别是"要不要打断"——把步骤写进汇报队列，Router 就成了日志消费者，这和记忆
里删掉的"日志冒充记忆"是同一个错误。

### 三个实现上的判断

**① 等级是算出来的，不是模型说的。**
`escalationLevel(previous)` 是纯函数，`previous` 由宿主从**步骤流**里数出来
（`step.text.startsWith('请示：')`），不是内存计数器。理由：进程重启后内存计数器归零，同一件事
就会第二次插队——而你只会觉得"它怎么又问一遍"。步骤流是持久的，数它得到的是事实。

**② 交回之后，任务跑完也不许把线按回去。**
这是最容易写错的一处：`hand_back` 把线放回 `open`，然后手上的活照旧跑完，`reportToThread`
一看 `accepted` 就把线改成 `done`——**交回等于没发生**，你还以为有人会重新接。所以
`reportToThread` 会先看一眼"这条任务交回过没有"。

顺手定下的语义：**交回不回滚改动**（写过的东西留着，那是事实），只是不再往下做、不再收这条线
的新事件。

**③ `decide` 时把线停在 `waiting`。**
它在等人做决定，这时候"在跑"是假的——线上要是一直观显示"在跑"，你就不会去看。

### 顺手撞出同一个 bug 的第二份拷贝：汇报的顺序不稳定

写用例时撞出来的：同一个毫秒落两条汇报（一次请示 + 一次终局、一次交付 + 一次超预算），
`ORDER BY created_at DESC` 的次序是**未定义**的。而汇报的顺序会进 Router 的输入——顺序每轮
都可能变，既吃不到提示词缓存，也让人以为系统在抽风。

`07-memory.md` §19 修过一次同一个形状的 bug（记忆列表），这次是 `report` 的四条查询
（队列、带线的队列、某条线的汇报、待宣告的汇报）。次级键一律 `rowid`。

**这个 bug 只有"断言顺序"的用例抓得到**：断言"包含"的用例全绿——第一次跑还是在单文件里过的，
整个套件一起跑才红。

### 用例

`escalateTool.test.ts`（7 条）：等级规则（0 → decide，其余 notify）、问题/试过/建议一起交上去、
两种回答的话不一样、没有任务或问题太短都不问、交回说清"别再往下做"、交不了把原因说出来、
没说原因不交回。

`workThreadReport.test.ts`（+5，端到端，真库真步骤）：两次请示 decide→notify 且线停在
`waiting`、请示里带上"试过/建议"、**正常干完的活只留一条 silent 记录**（队列为空、没有请示行）、
交回之后订阅空了且线回 `open`、**交回之后跑完也不许把线按回去**。

### 这一层之后

①②③④ 四层能力里，①②③齐了。剩下 E4（静默线）和 §11 那张诚实清单。

## 15. E4 已落地：静默线

### 只做了后一半，而且说清为什么

原文 §3.4 的那个例子是两个动作：**提前跑** + **说不说**。我们只做后一半。

前一半需要「后台有富余算力」这个前提。我们是单机、单个人的机器，提前跑就是抢你自己的
时间——`04-superagent-check.md` §1 那条判断不变。

后一半几乎不花新代码，因为两样东西都是现成的：**执行**是任务，**判据**是验收闸门。缺的只是
一条线级标记和一条汇报规则：

> 静默线上的汇报**永远不是 `decide`**。闸门过了 → `notify`；没通过（或根本没有闸门）→
> `silent` + 归档。

为什么"永远不 decide"：`decide` 的意思是「我要你放下手上的事」，而投机的前提恰恰是这件事
还没有确定性价值。

### 落到了哪

| 东西 | 在哪 |
|---|---|
| `thread.speculative`（默认 0，老库不动） | `schema.ts` 的 V40 |
| 开线时带上 | `workDispatch` / Router 的 `open_line_of_work(speculative)` |
| 汇报分级 | `threadOutcomeFor(task, { speculative })`（纯函数，五条用例） |
| 请示也降级 | `workService.escalateFor` |
| 超预算只说一次、且不插队 | `workService.reportToThread` |

### 三个容易漏的地方

**① 标记落在线上，不是任务上。** 规矩是这条线的规矩，而且它必须在派第一个任务**之前**就定
下来——否则第一次跑完就已经打扰过他了。

**② 同一个身份已有线时不改它的性质。** `openThread` 是"有就并进去"，那条已有的线不是投机
开的；把 `speculative` 盖上去，会让一条他明确要过的活从此不再报"没通过"。用例锁住了这一条。

**③ 没有闸门的静默线归档，不是"通过"。** `UNVERIFIED_GATE` 是一个永远成功、什么都证明不了
的命令。静默线上这等于"我不知道它对不对"——那就更不能拿它去换他的一次注意。

### 用例

`threadOutcome.test.ts`（+5）：过了才 notify、没通过归档、跑挂了也不 decide、没有闸门就归档、
非静默线不受影响。

`workDispatch.test.ts`（+3）：标记落在线上、普通派活不是静默线、已有线上不被改写。

`workThreadReport.test.ts`（+2，端到端）：跑通了一条 notify 进队列；静默线上的 `escalate`
只 `notify`，且线不回 `waiting`（没人需要为它做决定）。

### 这一层之后

原文对 Worker 层的每一条要求，现在都有了落点或有理由的"不做"（§11）。四期下来补的其实是
同一件事的三个面：**它看到的、它能想到的、它能说的**。

## 16. 团队：拆开之后谁收口（W1）

原文那句「也可以本身就是一个 Agent Team」以前只做了一半：`decompose_task` 会拆，但**拆开之后
没有人收口**。补齐的是三样东西，不是一个新概念——**等**（`collect` 阶段）、**收**（`TaskChild`）、
**谁说**（一条线的状态由根任务决定）。全文见 `09-team.md`。

三处在这一层最容易写错，记在这里：

1. **收口一次的真实用途不是等，是让下一轮看得见子任务。** 子任务秒回的时候，父如果直接验收，
   交出的是一份**不含子任务成果**的交付物，而它会通过验收（闸门只判父自己的目录）。
2. **子任务的 `decide` 降级成 `silent`。** 子任务失败时能判断"该怎么办"的是父，不是你——
   让它直接进队列，等于把中间状态当结论端上来。例外只有 `escalate`。
3. **等待用 `runtime.sleepUntil`，不用 `await setTimeout`。** 睡是一次提交，占不着进程，重启
   接着睡；后者重启之后什么都不剩。

顺带一提：pi 1.4.0 其实有现成的 join 原语（`{ status: 'waiting', on, policy }`），我们没用——
它要求 `on` 里的任务在**同一个 Harness** 里，而团队成员天然在别的 Harness 里（一人一份存储）。
为了一个语法糖放弃隔离粒度，是拿存在的理由换方便。
